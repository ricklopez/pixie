01 / The scattered pieces

Your next data source
is already in a browser.

A portal with no API. A script on someone’s laptop. A workflow that gets the job done—until the page changes, the session expires, or someone else needs to run it.

Browser automation is becoming part of our data infrastructure. It needs the contracts, lifecycle, and visibility we expect from an API framework.

02 / Give the pieces a contract

Show it once.
Build a service around it.

Inspired by LoopBack’s approach to API development, Pixie puts browser workflows behind typed inputs, structured outputs, versioned endpoints, and checks you can inspect.

Give consumers an immutable revision and an API contract.

05

Invoke the endpoint from another application and inspect its run evidence.

03 / Intelligence with a visible trail

Jev takes the next step.
Pixie checks where it lands.

Jev UltraFast proposes browser actions from what it observes. Pixie applies the workflow’s policy, executes allowed actions, and independently verifies the outcome before accepting a result.

API requestTyped input
Published workflow revision
Jev UltraFastObserve the page
Propose the next action
Pixie runtimeCheck the policy
Execute in the browser
Verified resultCheck postconditions
Return data and evidence

The runtime repeats observe, propose, and execute until the task completes or needs review.

See the decisions

Inspect the run’s visual flow, proposed actions, policy decisions, and verification results in Studio.

Keep the evidence

A completion claim is only part of the story. Checkpoints and independent checks determine whether the result is accepted.

Make exceptions explicit

Ambiguous targets and failed checks become reviewable outcomes. Consumers can tell when a run needs attention.

04 / Start with something tangible
Any Website.
Callable operations.
Pixie turns an ordinary browser-based app into an API. A client requests a change, Jev operates the visible browser, and Pixie verifies what actually happened.
  1. C
    Create a taskAdd “pixie-demo groceries” and verify it appears exactly once.
  2. R
    Read the listReturn structured task data from the browser app.
  3. U
    Update a taskChange the intended task and verify the new value.
  4. D
    Delete a taskRemove the intended item and check that other tasks remain unchanged.
Local developer workflow · after repository setup
pixie init ~/pixie-project
cd ~/pixie-project
pixie doctor
pixie dev

# Record and define in Studio.
# Then test your automation:
pixie test <automationId>
pixie publish <automationId>
The CLI runs from the repository; it is not published to npm. Live Jev runs require a configured model key.

05 / A foundation to build on
Browser workflows.
Durable service boundaries.
The goal is bigger than running a script: reusable data sources that applications, MCP servers, and agent tools can call through the same explicit contract.
For applications
Consume a versioned API instead of embedding browser-control logic in every integration.
For MCP servers
Use the API contract as a foundation for exposing workflows as tools. MCP packaging is an extension direction.
For agents
Give agents bounded operations with defined inputs and observable outcomes.
